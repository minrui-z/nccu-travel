## 具體發現

### UI-01 · P1 ·「前往修改」沒有定位到錯誤欄位

- 位置：`app/check-form.tsx` 的 `destinationForIssue`／`goTo`、`app/page.tsx` 的 `navigate`、`app/trip-form.tsx` 的 `activeId`。
- 初次證據：導覽只呼叫 `onNavigate(target.tab)` 及設定預覽 highlight；沒有使用完整 `issue.path` 選出錯誤日期、費用或輸入欄位。日期問題傳入的 `focus='days'` 也不屬於預覽支援的 `day:<id>`。
- 影響：例如後段日期未填城市，點修改後看到第一天，使用者仍須自行找出錯誤日。鍵盤使用者的焦點也沒有前往修正位置。
- 修正：以完整 `issue.path` 傳送導覽要求，`lib/issue-navigation.ts` 解析相應日期／區段；啟用日期群組、展開必要區塊，透過 `data-field-path` 捲至並聚焦實際控制項，旁邊呈現同一則錯誤。
- 狀態：已修正。隔離瀏覽器確認錯誤連結選到合併欄中的目標日，工作記要取得實際鍵盤焦點且 `aria-invalid=true`。
- 分類／參考：錯誤恢復、鍵盤操作；WCAG 2.4.3、3.3.1、3.3.3 相關檢查。建議 `/impeccable harden`。

### UI-02 · P1 · 200% 桌面縮放會失去草稿操作

- 位置：`app/globals.css` 的 `@media (max-width: 800px)`，`.draft-state` 與 `.draft-actions`。
- 初次證據：CSS 直接 `display:none`；1440px 桌面視窗放大到 200% 時，CSS 可用寬度約為 720px，會命中此規則。
- 影響：看不到儲存成功／失敗，也找不到載入範例與清空。使用者要求桌面版，不代表可以在桌面放大時移除功能。
- 修正：800px 以下保留 `.draft-state`，`.draft-actions` 改用可換行 flex，標題區允許換行。
- 狀態：已修正。隔離瀏覽器在 720px 下確認草稿狀態及「清空」可見，頁面 `scrollWidth` 不超過視窗寬度。
- 分類／參考：版面與縮放；WCAG 1.4.4、1.4.10 相關檢查。建議 `/impeccable adapt`。

### UI-03 · P1 · 放大預覽缺少焦點管理與 Escape

- 位置：`app/report-preview.tsx`、原 `.large-preview` CSS。
- 初次證據：`large` 只加入 `position:fixed` 的 CSS 類別。沒有 dialog 語義、Escape 處理或背景焦點隔離。
- 影響：Tab 可走到放大預覽後方的表單；使用者可能在看不到輸入位置時修改資料，Escape 也不能關閉。
- 修正：改成原生 `<dialog>`／`showModal()`；背景由瀏覽器設為不可操作，另補 Tab／Shift+Tab 在首尾控制項間循環。Escape 可關閉，關閉後明確還原焦點至「放大預覽」。對話框有「原表放大預覽」名稱及限定視窗大小的捲動版面。
- 狀態：已修正。針對檔案的 lint 及 detector 通過；隔離瀏覽器確認 dialog 開啟、Tab／Shift+Tab 留在對話框、Escape 關閉並還焦。
- 分類／參考：可及性與操作控制；WCAG 2.1.1、2.4.3、4.1.2 相關檢查。建議 `/impeccable harden`。

### UI-04 · P2 · 切換學生版後可能仍標示「原附表」

- 位置：`app/report-preview.tsx` 的 `page`／`sheet`／`main`。
- 初次證據：一般版先選附表 `page=1`，切學生版後 `sheet` 回退第一張，但工具列、ARIA 與高亮仍用原來 `page=1`。
- 影響：畫面實際是學生主表，文字卻說附表，輸入高亮失效。
- 修正：新增 `effectivePage`，工作表、工具列、預覽名稱、高亮與頁面按鈕狀態共用同一個有效頁碼；頁面按鈕另加 `aria-pressed`。
- 狀態：已修正。針對檔案的 lint 及 detector 通過；隔離瀏覽器實測一般版先選附表，再切學生版，工具列恢復「主表單頁」。其 ARIA 與高亮同樣使用已核對的 `effectivePage` 分支。
- 分類：狀態一致性。建議 `/impeccable harden`。

### UI-05 · P1 · 草稿未成功取代卻顯示成功

- 位置：`app/use-draft.ts` 的 `replaceDraft`、`app/page.tsx` 的確認動作。
- 初次證據：舊草稿備份失敗時 `replaceDraft` 直接 return；呼叫端卻 `void replaceDraft(next)`，立即顯示「已清空」或「已載入」。
- 影響：無法寫入或備份的瀏覽器仍得到成功訊息，與畫面實際資料不符，使用者不能判斷現在保留的是哪份內容。
- 修正：`replaceDraft` 回傳布林結果，呼叫端 await；成功後才切頁及顯示成功，失敗保留資料並顯示「未取代草稿」。儲存狀態加入 `role=status`，失敗、無法讀取或暫停時改用紅色狀態文字及圓點。
- 狀態：已修正。隔離瀏覽器模擬舊草稿無效且備份失敗，確認顯示備份失敗，不出現「已清空本機草稿」。
- 分類／參考：錯誤恢復與狀態訊息；WCAG 4.1.3 相關檢查。建議 `/impeccable harden`。

### UI-06 · P1 · 核對通過與 XLS 容量錯誤不同步

- 位置：`app/page.tsx` 的 `mapped.errors`、`app/check-form.tsx` 的完整狀態。
- 初次證據：核對頁只計算 `calculation.issues`，原表文字容量錯誤另留在預覽；因此可以看到「表內必填資料已填齊」，下載時仍被拒絕。
- 影響：使用者無法靠核對頁完成送出前修正，尤其右側預覽位於下方或未在視窗內時。
- 修正：`mapped.errors` 傳入核對頁 `exportIssues`，與計算錯誤共同構成 `blockingCount`；核對頁另列「需修正：表格文字」及各欄容量說明。
- 狀態：已修正。隔離瀏覽器填入超長備註後，確認核對頁呈現表格文字問題及「下載前須修正」，不再顯示檢查通過。
- 分類：錯誤恢復與實作一致性。建議 `/impeccable harden`。

### UI-07 · P1 · 三種小字顏色對比不足

- 位置：`app/globals.css` 的輸入 placeholder、`.preview-disclaimer`、`.paper-tabs button`。
- 初次量測：依來源 CSS 的實色與 WCAG 相對亮度公式計算，`#91a0af`／白色為 2.67:1；`#718295`／`#f7f9fb` 為 3.73:1；`#6b7e92`／`#eaf0f5` 為 3.64:1。這些文字為 10–14px，不能使用大字的 3:1 門檻。
- 影響：欄位例子、預覽限制與未選頁籤對低視力使用者不易閱讀。
- 修正：三處統一使用 `--muted-foreground: #52677d`，placeholder 明確設為不透明。
- 狀態：已修正並重新核算 CSS 色值。新色對白底為 **5.84:1**、預覽註解底 `#f7f9fb` 為 **5.53:1**、頁籤底 `#eaf0f5` 為 **5.09:1**，均超過一般小字 4.5:1；這不是其他全部顏色組合的合規保證。
- 分類／參考：WCAG 1.4.3 對比。建議 `/impeccable polish`。

### UI-08 · P2 · 欄位元件的錯誤／提示支援沒有接完整

- 位置：`app/fields.tsx` 及各表單呼叫端。
- 初次證據：`Field`／`Area` 已提供 `error`、`aria-invalid`、`aria-describedby`，但原呼叫端沒有傳入任何 `error`；`Choice` 的 hint 也沒有關聯到 trigger。
- 影響：使用者改回原頁後看不到哪格錯誤；讀屏器不一定讀出下拉選單的適用條件。
- 修正：共用 `FieldIssues` context 依每個欄位的 path 取得錯誤，`Field`、`Area`、`Choice`、`CheckField` 均連接對應狀態。Choice 的提示／錯誤加入 id、`aria-describedby` 及 `aria-invalid`。
- 狀態：已修正，程式碼連結已核對；隔離瀏覽器的日期錯誤定位同時確認實際輸入欄 `aria-invalid=true`。沒有將所有選填欄位改為必填。
- 分類／參考：WCAG 1.3.1、3.3.1、3.3.2 相關檢查。建議 `/impeccable clarify`。

### UI-09 · P2 · 模板與 Worker 啟動失敗的恢復路徑不完整

- 位置：`app/page.tsx` 的 `download`。
- 初次證據：模板未載入且沒有計算錯誤時，訊息被改寫為「請先處理 0 項資料」；`new Worker` 位於 try 外，若同步拋錯，`exporting` 不會在 finally 恢復。
- 影響：載入問題被誤導為填表錯誤；受限環境中有機會一直停在「產生中」。此為程式碼可達的錯誤路徑，未對使用者環境注入故障。
- 修正：模板未就緒時獨立顯示模板載入或失敗說明；Worker 建構移入 try，finally 使用 `worker?.terminate()` 並恢復按鈕。
- 狀態：已修正。隔離瀏覽器模擬 Worker 建構同步失敗，確認顯示未產生檔案且「下載 XLS」重新可用。模板缺檔訊息分支另以程式碼核對。
- 分類：載入、錯誤恢復。建議 `/impeccable harden`。

## 已確認值得保留的設計

- 四步驟本身具有操作順序，因此 01–04 是有意義的流程編號；不屬於無用途裝飾。
- 國家→城市選單、起點／迄點與日支額地區分開，避免把交通路線誤當生活費依據。
- 合併欄旁明示同步修改天數；勾選與編輯分開，提供拆開、取消選取及不相容原因。
- 私人日期清空日支額及下方欄位，草稿恢復會正規化；費用不會被悄悄刪除。
- 原生勾選框有 label；多數圖示按鈕有中文名稱；欄位 input／textarea 有程式化 label。
- 表格有 caption、欄表頭與列標頭；匯率匯入和分組結果有狀態訊息；刪除費用有復原入口。
- 字型由同站提供，日常匯出不依賴後台；原生 XLS 在 Worker 產生，原表與計算資料分開。

## 認知負擔與操作情境

初次使用者最需要的是從核對頁直接修到缺漏欄位，而不是另一輪引導文案；本次已完成此導覽。熟悉報帳者可使用合併日期、批次套用與每筆費用來源，重複動作已有入口。UI-01、UI-02、UI-03 已優先修正並驗證，保留原有操作與視覺方向。

費用與匯率的條件很多，現有逐筆分區及可展開說明可以保留。避免把所有匯率來源、證明、缺漏提示都同時展開；需要手動處理時才呈現對應欄位。用語維持欄位名稱與具體動作，不恢復使用者要求移除的宣傳句與進位狀態標籤。

另兩項費用修正已整合：每筆外幣費用自動選用適用日期報價，手動值不被切頁覆蓋，費用頁未開啟時也會依新基準日期更新；單據總張數與每筆號碼分開，留白可先下載。它們不重複計入本報告的 9 項 UI 問題。
